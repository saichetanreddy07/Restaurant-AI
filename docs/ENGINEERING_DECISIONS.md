# Engineering Decisions

This guide records the reasoning behind the project’s main technology and design choices. These are pragmatic choices for a learning project with real operational rules, not universal recommendations.

## FastAPI and REST

**Choice.** FastAPI exposes resource-oriented REST endpoints, uses HTTP methods and status codes, and generates an OpenAPI reference from route declarations.

**Why.** The domain maps naturally to resources such as ingredients, recipes, inventory batches, and availability. FastAPI provides Pydantic integration, dependency injection, and interactive API docs with little framework overhead.

**Alternatives and trade-offs.** Flask would be smaller but needs separate validation and API documentation choices. Django REST Framework provides more built-in features than this API needs. GraphQL can support flexible client queries, but would add schema and resolver complexity for the current resource workflows.

**Advantages.** Typed route contracts, automatic request validation, explicit dependencies, and a convenient integration reference.

**Limitations.** The team must keep route handlers thin and choose carefully between synchronous and asynchronous database work; this application currently uses synchronous SQLAlchemy sessions.

**Choose something else when.** A full server-rendered product and built-in admin/auth are central (Django), or clients need deeply variable nested data selections (GraphQL).

**Interview Q&A.** *Why FastAPI?* It lets route contracts and validation stay explicit and generates OpenAPI documentation from code. *Why REST?* The operations are resource-oriented and map clearly to HTTP methods and status codes.

## Pydantic

**Choice.** Pydantic schemas validate request and response data at the API boundary; `pydantic-settings` reads application settings from environment configuration.

**Why.** Untrusted input should be checked before business operations, and schemas keep wire formats separate from ORM persistence models.

**Alternatives and trade-offs.** Manual validation offers full control but duplicates work and error handling. Dataclass-only contracts require additional validation tooling.

**Advantages.** Declarative field constraints, predictable serialization, and readable FastAPI validation errors.

**Limitations.** Schema validation cannot replace domain checks that require database state, such as whether a referenced recipe or ingredient exists.

**Choose something else when.** A system has a different established validation framework or needs specialized high-throughput serialization with a different contract model.

**Interview Q&A.** *Why separate schemas from ORM models?* API validation and persistence have different responsibilities; separate models avoid coupling external contracts to database details.

## SQLAlchemy 2 and MySQL

**Choice.** SQLAlchemy 2 declarative models and typed queries persist data in MySQL using request-scoped sessions.

**Why.** Ingredients, recipes, batches, and audit movements have clear relationships and need relational constraints and atomic updates. SQLAlchemy provides explicit query control; MySQL provides transactional relational storage.

**Alternatives and trade-offs.** Raw SQL may be preferable for a small set of highly specialized queries but requires more manual mapping. PostgreSQL is a strong relational alternative. A document database would make the connected entities and constraints less direct.

**Advantages.** Foreign keys, uniqueness, check constraints, joins, transactions, and a consistent Python model/query layer.

**Limitations.** ORM abstractions require query awareness, and schema changes need coordinated migrations. The app uses synchronous database access.

**Choose something else when.** Another SQL database better matches hosting or team expertise, or a workload is primarily document-shaped and does not depend on relational integrity.

**Interview Q&A.** *Why a relational database?* Recipe composition, inventory movements, and their references benefit from foreign keys and transaction guarantees. *How do you avoid hidden inefficient queries?* Queries are explicit and bulk availability reads use eager loading and set-based retrieval.

## Alembic

**Choice.** Alembic stores schema changes as versioned migrations integrated with SQLAlchemy metadata.

**Why.** Existing databases need incremental schema evolution; recreating tables from metadata would not safely preserve data.

**Alternatives and trade-offs.** Manual SQL provides direct control but makes versioning and consistency more manual. Other migration tools can be useful in multi-language environments but do not integrate as directly with SQLAlchemy models.

**Advantages.** Reviewable migration history and repeatable upgrades/downgrades.

**Limitations.** Autogenerated migrations require human review and production deployments need an intentional migration process.

**Choose something else when.** The organization standardizes on another migration tool or the application uses a different persistence stack.

**Interview Q&A.** *Why not `create_all()`?* It creates missing tables, but it is not a safe change history for evolving existing schemas.

## React, TypeScript, Vite, and feature modules

**Choice.** The frontend is a React 19 and TypeScript SPA built with Vite and organized around operational features.

**Why.** The product has interactive, data-heavy workflows that benefit from reusable components and typed service contracts. Vite provides a straightforward development and build workflow. Feature folders keep related screens and API access together.

**Alternatives and trade-offs.** A server-rendered framework could suit content-heavy pages and SEO; a larger frontend framework could be useful for a broad product but adds concepts the current app does not need. JavaScript alone has less setup but gives up compile-time contract checks.

**Advantages.** Responsive interactions, reusable UI, typed API data, and clear module ownership.

**Limitations.** A SPA requires client-side routing and API error/loading handling. TypeScript cannot guarantee runtime data validity by itself.

**Choose something else when.** Search indexing and server rendering are primary requirements, or the client has minimal interaction and can be rendered on the server.

**Interview Q&A.** *Why feature-based organization?* It groups components, types, and service calls by the business capability they implement, making changes easier to locate.

## Axios and TanStack Query

**Choice.** Axios is wrapped in a centralized API client; TanStack Query is installed and its provider is configured at the app root.

**Why.** A shared HTTP client centralizes base URL and common response behavior. Query provides a place for server-state caching as screens adopt it.

**Alternatives and trade-offs.** Browser `fetch` avoids a dependency but requires local handling for common HTTP behavior. Local React state/effects are simple for individual screens but repeat caching and request lifecycle concerns. Note: current feature pages primarily use local state/effects; TanStack Query is not yet their data-fetching mechanism.

**Advantages.** Central API configuration and an available server-state cache foundation.

**Limitations.** Merely configuring Query does not give screens caching benefits; adopting it should be incremental and consistent.

**Choose something else when.** A tiny application can use `fetch` directly, or the application’s framework already provides a server data layer.

**Interview Q&A.** *Is TanStack Query used by all features?* No. The provider is set up, but feature pages currently load data with local React state and effects.

## Tailwind CSS

**Choice.** Tailwind CSS v4 utility classes style the responsive application shell and feature pages.

**Why.** It supports a consistent visual system while keeping styling close to component markup, without introducing a separate component framework.

**Alternatives and trade-offs.** CSS modules or plain CSS offer isolated styles but require more naming and organization decisions. A UI kit can accelerate common components but brings its own design system and dependency.

**Advantages.** Responsive utilities and quick iteration with a small styling surface.

**Limitations.** Dense class lists can reduce readability unless components remain focused and repeated patterns are extracted.

**Choose something else when.** The team already owns a mature design system or prefers stylesheets with strict component isolation.

**Interview Q&A.** *How is UI consistency maintained?* Shared layouts and reusable components provide common structure while feature modules own their workflows.

## Domain decisions

### Layered backend

**Choice.** Routers, services, schemas, and persistence models have distinct roles. **Why.** HTTP handling, business rules, validation, and storage can change independently. **Alternative.** Putting everything in route handlers is initially quick but couples concerns. **Advantages.** Clear navigation and reusable service operations. **Limitations.** Small features may touch several layers. **Choose otherwise when.** A very small throwaway endpoint has no meaningful domain logic. **Interview Q&A.** *Where does inventory consumption logic live?* In a service so the router remains an HTTP boundary.

### Batch stock and movement history

**Choice.** Inventory batches hold remaining quantities; subsequent movements are recorded in positive-quantity transaction rows, while ingredient `current_stock` is synchronized to active batch totals. **Why.** The system needs lot traceability and an explainable stock history, while the aggregate supports simpler availability reads. **Alternative.** A single ingredient quantity is simpler but loses lot-level expiry and supplier detail. **Advantages.** Expiry-aware selection and audit records. **Limitations.** The aggregate must remain synchronized with batches during every relevant write. **Choose otherwise when.** Lot traceability and expiry do not matter. **Interview Q&A.** *Why keep both batch quantities and an ingredient total?* Batches preserve detail; the synchronized total is a convenient aggregate used by catalog and capacity views.

### FEFO consumption and read-only availability

**Choice.** Consumption orders eligible batches by expiry, then receipt date, and processes deductions atomically. Availability computes capacity without writes. **Why.** FEFO prioritizes perishable stock and atomicity prevents partial consumption; separating a read calculation from a write operation makes the contracts explicit. **Alternative.** FIFO alone ignores differing expiry dates; updating stock during availability checks would be surprising and unsafe. **Advantages.** Predictable waste-aware deductions, rollback on insufficient stock, and safe capacity reads. **Limitations.** The algorithm assumes batch expiry dates and quantities are maintained correctly. **Choose otherwise when.** Stock is nonperishable or domain policy mandates a different allocation method. **Interview Q&A.** *What makes consumption atomic?* All recipe requirements are checked first; batch deductions and audit rows then run in one database transaction.

### Menu catalog and recipes

**Choice.** Menu items hold customer-facing category and price; recipes hold preparation requirements, with at most one recipe per menu item. **Why.** Selling a product and preparing it are related but distinct concerns. **Alternative.** Storing ingredients directly on menu items conflates commercial and kitchen responsibilities. **Advantages.** Catalog and preparation can evolve separately. **Limitations.** A menu item without a recipe cannot have calculated availability. **Choose otherwise when.** A product has no preparation formula or the domain needs multi-variant recipes. **Interview Q&A.** *Why separate a menu item from its recipe?* Price and classification describe the sale; ingredient requirements describe preparation.
